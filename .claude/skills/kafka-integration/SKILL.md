# Kafka для системного аналитика

Скилл построен на видео Андрея Царёва (ссылка в `metadata.source`). Всё, что не из видео, помечено **[дополнение]** — это уточнения по документации Kafka, а не слова автора.

## Как работать с запросом

- **Пишут постановку / ТЗ на интеграцию** → пройди «Чек-лист постановки» ниже по пунктам и задай пользователю вопрос по каждому незаполненному пункту. Не придумывай ответы за бизнес: порядок, гарантия доставки и retention — решения, а не значения по умолчанию.
- **Проверяют чужую постановку** → сверь её с чек-листом и перечисли, чего не хватает, начиная с самого рискованного: нет ключа при важном порядке, at least once без идемпотентности получателя, нет DLQ.
- **Просят объяснить понятие** → бери определения из раздела «Модель», с примером на заказах (`orders-created`, ключ = ID заказа).
- **Готовятся к собеседованию** → раздел «Ловушки», каждую ловушку проговаривай как вопрос и ответ.
- **Выбирают брокер** → раздел «Kafka или RabbitMQ».

## Зачем вообще брокер

Когда N сервисов напрямую вызывают API друг друга, связи растут лавиной («сервисный спагетти»). Синхронный вызов означает, что тормоза или падение получателя бьют по отправителю. Брокер — это прослойка: продюсеры пишут события, консюмеры читают, а отправитель «выстрелил и пошёл дальше», не дожидаясь ответа. Это асинхронное взаимодействие, в отличие от запроса-ответа в REST.

## Модель

- **Kafka** — не очередь в привычном смысле, а распределённая платформа потоковой обработки событий, то есть распределённый **лог**. Сообщения лежат на диске и не исчезают после чтения: один поток могут независимо и в своём темпе читать хоть 100 консюмеров, хоть через неделю.
- **Брокер** — сервер, который хранит данные и обслуживает чтение и запись. Несколько брокеров образуют **кластер**, это даёт масштаб и отказоустойчивость.
- **Продюсер** пишет события, **консюмер** читает.
- **Метаданные кластера** (какие брокеры живы и кто за что отвечает) раньше хранил ZooKeeper, а теперь их хранит сам кластер в режиме **KRaft**. [дополнение] KRaft готов к проду с версии 3.3, в Kafka 4.0 ZooKeeper удалён совсем.
- **Топик** — именованный поток однотипных событий, например `orders-created`. Это логическая сущность, а не единица хранения.
- **Партиция** — физическая часть топика: независимая, строго упорядоченная лента сообщений. Партиции нужны для трёх вещей:
  1. **масштаб**: партиции раскидываются по брокерам, запись и чтение идут параллельно;
  2. **порядок**: он гарантирован только внутри партиции;
  3. **параллельное чтение**: каждому консюмеру группы достаётся своя партиция.
- **Ключ сообщения** (необязательный). Если ключ задан, Kafka хеширует его и по хешу выбирает партицию: одинаковый ключ → всегда одна партиция → порядок между этими сообщениями сохраняется. Если ключа нет, сообщения размазываются по партициям ради баланса нагрузки, без гарантии порядка.
- **Offset** — порядковый номер сообщения внутри партиции, «номер строки». Консюмер запоминает, до какого offset дочитал, и после падения продолжает с него, а не сначала.
- **Консюмер-группа** — консюмеры с одним `group.id`, решающие одну задачу. Внутри группы одна партиция в каждый момент принадлежит ровно одному консюмеру:
  - 6 партиций и 3 консюмера → по 2 партиции каждому;
  - 6 и 6 → по одной;
  - 6 и 7 → седьмой простаивает, партицию на двоих не делят.
- **Ребалансировка**: консюмер упал или добавился → Kafka заново распределяет партиции между живыми консюмерами группы.
- **Разные группы читают топик независимо**: группа `billing` и группа `analytics` получат все сообщения целиком, и у каждой свой offset.
- **Репликация**: у партиции есть фактор репликации, то есть число копий на разных брокерах.
  - Одна копия — **лидер**, она принимает чтение и запись. Остальные — **фолловеры**, они копируют данные с лидера.
  - Если лидер упал, новым лидером становится фолловер из **ISR** (in-sync replicas). Отставший фолловер выпадает из ISR и лидером стать не может, пока не догонит.
  - На проде фактор обычно 3. В локальной песочнице с одним брокером — 1.
- **Retention** — сообщение хранится заданное время (по умолчанию 7 дней) или до лимита по размеру, *независимо от того, прочитали его или нет*. Поэтому можно поднять нового консюмера и прочитать историю, или перемотать offset назад и переобработать события после бага в получателе.

## Гарантии доставки

**`acks` — настройка продюсера:** сколько подтверждений ждать от брокера, прежде чем считать сообщение отправленным.

| `acks` | Что ждёт продюсер | Риск |
|---|---|---|
| `0` | ничего | быстро, но потерю никто не заметит |
| `1` | подтверждение лидера | лидер принял и упал до репликации → сообщение потеряно |
| `all` (`-1`) | подтверждение всех реплик из ISR | самое надёжное, но медленнее |

[дополнение] С Kafka 3.0 у продюсера по умолчанию `acks=all` и включена идемпотентность. В старых клиентах и настройках команды может быть иначе, поэтому проверяй, а не предполагай.

**Модели доставки:**

- **At most once** — может потеряться, но не задублируется. Подходит для метрик, heartbeat, сырых технических логов: там дубль искажает картину сильнее разовой потери, а объём слишком велик, чтобы бороться за каждое сообщение.
- **At least once** — не потеряется, но может задублироваться. Самый частый вариант, «рабочая лошадка» бизнес-интеграций: заказы, уведомления, статусы. Консюмер коммитит offset *после* обработки. Если он упал между обработкой и коммитом, при перезапуске обработает сообщение снова. Работает, только если получатель **идемпотентен**, то есть сам распознаёт и гасит дубли (например, по ID заказа).
- **Exactly once** — без потерь и без дублей. Нужен там, где неприемлемо и то и другое: списание денег, начисление кэшбэка и бонусов. Это не бесплатная опция по умолчанию: её осознанно включают и тестируют, и нужна она далеко не всегда. Для большинства интеграций хватает at least once плюс идемпотентной обработки у консюмера.

**Как это устроено технически:**

- **Идемпотентный продюсер**: каждое сообщение получает номер. Если продюсер из-за сетевого сбоя отправляет его повторно, брокер узнаёт дубль по номеру и отбрасывает его. Это та же идея, что идемпотентность в REST.
- **Транзакции** объединяют в одну атомарную операцию чтение из топика, обработку и запись результата в другой топик.

## Kafka или RabbitMQ

**Плюсы Kafka:** огромная пропускная способность, горизонтальное масштабирование, хранение истории с повторным чтением, много независимых консюмеров на один поток.

**Минусы Kafka:** сложнее администрировать; нет гибкой маршрутизации из коробки, топики линейные. В RabbitMQ для этого есть exchange с правилами роутинга.

**Как выбрать:**
- Нужен **поток событий**, который надо хранить, переигрывать и раздавать многим независимым читателям → Kafka.
- Нужна **очередь задач** с гибкой маршрутизацией и приоритетами при умеренных объёмах → RabbitMQ, его проще поддерживать.

## Чек-лист постановки интеграции

Минимум в любой постановке: **откуда читаем, куда кладём, что кладём** — источник, топик назначения и контракт события. Партиции и ребалансировка — зона разработчика. Но в постановке должно быть зафиксировано следующее:

1. **Контракт события**: обязательные поля и их смысл — «что должно передаваться», а не «как получится».
2. **Важен ли порядок событий по сущности.** Если да, ключом сообщения обязательно указывается ID этой сущности (например, ID заказа: создан → оплачен → отгружен приходят по порядку).
3. **Гарантия доставки**: хватает at least once или нужен exactly once, и почему.
4. **Идемпотентность получателя**: умеет ли он обрабатывать дубли и по какому полю их распознаёт. Для at least once это обязательное условие.
5. **Невалидные сообщения**: куда они уходят. Есть ли **DLQ**, чтобы битое сообщение не блокировало партицию.
6. **Retention**: хватает ли стандартного срока (обычно 7 дней), чтобы поднять нового консюмера или переиграть события задним числом.

## Ловушки, которые спрашивают на собеседовании

- «Kafka гарантирует порядок?» → только **внутри партиции**, не в рамках топика. Уточняй: «в рамках чего?»
- «Сообщение удаляется после чтения?» → нет, оно живёт до истечения retention, независимо от чтения.
- «Добавим консюмеров, станет быстрее?» → только до числа партиций. Лишние консюмеры в группе простаивают.
- «Две группы читают топик — делят сообщения?» → нет, каждая получает всё, у каждой свой offset.
- «`acks=1` надёжно?» → нет: лидер может упасть до репликации.
- «Включим exactly once везде?» → дорого и сложно. Обычно достаточно at least once плюс идемпотентного получателя.
- «Просто увеличим число партиций у живого топика?» → это чувствительная настройка, Kafka UI прямо предупреждает. [дополнение] Партиция выбирается по хешу ключа от числа партиций, поэтому после увеличения тот же ключ может попасть в другую партицию, и порядок по сущности на стыке ломается. Фактор репликации и число партиций закладывают заранее.

## Песочница: потрогать руками

В видео Kafka поднимается одним `docker-compose.yml` в режиме KRaft с Kafka UI на `localhost:8080`. Сам файл автор выложил в Telegram, в видео его нет. Что показано:

1. `docker compose up -d` → открыть Kafka UI.
2. Создать топик `orders-rejected`: 3 партиции, фактор репликации 1 (брокер один, реплицировать некуда).
3. Отправить сообщение из UI. UI требует выбрать партицию явно, и сообщение попадает туда, куда указали, а не по ключу.
4. Отправить из консольного продюсера несколько сообщений с ключами `order1`, `order2`: все сообщения одного ключа ложатся в одну партицию.
5. Запустить консюмеров с одним `group.id` (`rejected-group`):
   - 2 консюмера на 3 партиции → 2+1;
   - убить одного → ребалансировка, оставшийся читает все три;
   - 3 консюмера → по одной партиции;
   - 4-й простаивает.
6. Отправить сообщение из Postman через REST-прокси. Без партиции он ругается, с несуществующей партицией (3 при партициях 0–2) отвечает 400 Bad Request.
7. В настройках топика в UI виден retention (по умолчанию 7 дней). Число партиций и фактор репликации на живом топике менять опасно.

[дополнение] Команды для самостоятельного повтора (образ `apache/kafka`, внутри контейнера, скрипты в `/opt/kafka/bin`):

```bash
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders-rejected --partitions 3 --replication-factor 1
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders-rejected --property parse.key=true --property key.separator=:
#   order1:{"status":"created"}
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders-rejected --group rejected-group --property print.key=true --property print.partition=true
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group rejected-group
```

## Итог в пяти строках

1. Kafka — распределённый лог событий, а не очередь: читают независимо, хранят заданное время.
2. Топик — логический поток, физически разбитый на партиции. Порядок есть только внутри партиции.
3. Ключ = ID сущности, если порядок по ней важен.
4. Группа делит партиции между своими консюмерами, а разные группы читают топик независимо.
5. В постановке минимум — источник, назначение и контракт события, а дальше чек-лист выше.
