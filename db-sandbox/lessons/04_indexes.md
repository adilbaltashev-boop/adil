# Урок 04. Оптимизация БД. Работа с индексами

Занятие курса: 22 марта 2027. Практика: [`solutions/04_indexes.sql`](../solutions/04_indexes.sql).

## Нефункциональные требования и БД

Индексы появляются не «потому что так принято», а из НФТ. Аналитик формулирует их измеримо:

| НФТ | Как сформулировать | Что это значит для БД |
|---|---|---|
| Время ответа | «Поиск клиента по ИИН ≤ 200 мс для 95% запросов» | индекс (уникальный) на `clients.iin` |
| Нагрузка | «До 50 заявок в секунду в пик (конец месяца)» | каждый индекс замедляет вставку — не плодить лишние |
| Объём | «5 млн платежей в год, хранить 5 лет» | 25 млн строк: без индекса по `loan_id` выписка будет читать всю таблицу |
| Отчётность | «Отчёт по просрочке формируется ночью, ≤ 10 мин» | частичные индексы, а иногда отдельная реплика для отчётов |
| Доступность | «Изменения схемы без остановки сервиса» | `CREATE INDEX CONCURRENTLY` (см. урок 02) |

## Что такое индекс

Отдельная упорядоченная структура (обычно B-дерево) «значение → где лежит строка». Как
алфавитный указатель в книге: найти страницу быстро, но указатель надо обновлять при каждой
правке текста и он занимает место.

| Индекс ускоряет | Индекс замедляет / стоит |
|---|---|
| `WHERE колонка = …`, диапазоны, `ORDER BY`, `JOIN` по колонке | каждый `INSERT`, `UPDATE` колонки, `DELETE` |
| уникальность (`UNIQUE`) | место на диске (в песочнице индексы бывают больше таблицы) |

## Как читать план (`EXPLAIN ANALYZE`)

- `Seq Scan` — прочитана вся таблица. Нормально для маленьких таблиц и запросов «почти всё».
- `Index Scan` / `Index Only Scan` / `Bitmap Index Scan` — использован индекс.
- `actual time`, `rows` — реальность; `cost`, `rows` в первых скобках — оценка планировщика.
  Если оценка и реальность сильно расходятся — устарела статистика (`ANALYZE таблица`).
- `Execution Time` — итоговое время. Сравнивай его «до» и «после».

В DBeaver: выдели запрос → ⌘ + ⇧ + E, или выполни `EXPLAIN ANALYZE …` как обычный запрос.

## Что показывает практика (цифры с PostgreSQL 16, у тебя будут свои)

| Шаг | До индекса | После |
|---|---|---|
| Платежи одного кредита в таблице на 1 млн строк | ~27 мс, Seq Scan | ~0,25 мс, Index Scan |
| Вставка 200 000 строк | ~170 мс без индексов | ~2 200 мс с шестью индексами (≈ в 13 раз медленнее) |

## Виды индексов, которые нужны аналитику

| Вид | Пример | Когда |
|---|---|---|
| Обычный | `(loan_id)` | поиск/JOIN по внешнему ключу — почти всегда |
| Уникальный | `UNIQUE (iin)` | бизнес-правило «одно значение на всю таблицу» |
| Составной | `(status, created_at)` | фильтр по одной колонке + сортировка по другой; порядок колонок важен |
| Частичный | `(issued_on) WHERE status IN ('overdue','written_off')` | ищем редкое подмножество |
| По выражению | `(lower(last_name))` | в запросе всегда одно и то же выражение |
| `text_pattern_ops` | `(last_name text_pattern_ops)` | `LIKE 'Ахмет%'` при не-C сортировке |
| GIN | `USING gin (response)` | поиск внутри JSON (`@>`), полнотекстовый поиск |

## Проблемы избыточной оптимизации

1. Индекс на каждую колонку «на всякий случай» — вставка платежей становится медленной, база растёт.
2. Индексы-дубли: `(loan_id)` не нужен, если уже есть `(loan_id, installment_no)` — левая часть составного работает сама.
3. Индекс по колонке с 2–5 значениями (`channel`, `status`) почти никогда не используется — планировщик выберет Seq Scan.
4. Неиспользуемые индексы: смотри `pg_stat_user_indexes.idx_scan = 0` на проде после нескольких недель работы.

## Шаблон постановки задачи: индекс

```
Задача: добавить индекс <имя> на <таблица>(<колонки>) [WHERE <условие>]
Зачем: запрос <какой/где используется> выполняется <X мс>, НФТ — <Y мс>.
План до: <Seq Scan …, Execution Time …>
Ожидаемый эффект: <Index Scan, ≤ Y мс>.
Цена: размер индекса ≈ <…>, замедление вставки в <таблица> — <оценка>; частота вставок <…>/сек.
Как накатывать: CREATE INDEX CONCURRENTLY (без блокировки записи), откат — DROP INDEX CONCURRENTLY.
Проверка: EXPLAIN ANALYZE запроса после выката; idx_scan в pg_stat_user_indexes растёт.
```

В конце практики скрипт удаляет всё, что создал, и песочница возвращается к исходному виду.
