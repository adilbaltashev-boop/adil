# Урок 03. Проектирование распределённых БД

Занятие курса: 15 февраля 2027. Практика: [`solutions/03_distributed.sql`](../solutions/03_distributed.sql).

## SOA и микросервисы — коротко

| | Монолит | SOA | Микросервисы (MSA) |
|---|---|---|---|
| Единица | одно приложение | крупные сервисы под домены бизнеса, часто общая шина (ESB) | маленькие сервисы под одну бизнес-способность |
| База данных | одна общая | часто общая или несколько крупных | **у каждого сервиса своя**, чужую напрямую не читать |
| Связь | вызов функции | ESB, SOAP | REST/gRPC + события (Kafka, RabbitMQ) |
| Транзакции | одна ACID-транзакция | распределённые транзакции | локальные транзакции + саги и события |

## Как резать кредитный модуль

Сервис = бизнес-способность со своими данными и своей командой:

| Сервис | Отвечает за | Свои таблицы | Чужие данные, которые ему нужны |
|---|---|---|---|
| Client Service | профиль клиента, KYC | `clients` | — |
| Origination Service | приём заявки, скоринг, бюро | `applications`, `bureau_checks` | ИИН и доход клиента — **снимок** на момент подачи |
| Loan Service | договор, график, залоги | `loans`, `schedule` | `client_id` (денормализован), `application_id` |
| Payment Service | приём платежей | `payments`, `outbox` | номер договора |

Ключевые решения, которые аналитик пишет в требованиях:

1. **Нет FOREIGN KEY между сервисами.** Целостность обеспечивается процессом: событиями,
   проверкой при вызове API, сверками. Значит, «осиротевшие» ссылки возможны — нужен регламент сверки.
2. **Снимок vs ссылка.** Заявка хранит доход на момент подачи — если клиент потом изменит доход,
   решение по заявке не должно «поплыть». Это бизнес-требование, а не техническое.
3. **Денормализация.** Loan Service хранит `client_id`, чтобы на «покажи кредиты клиента» не ходить в Origination.
4. **Справочники копируются** (регионы, продукты) — нужен владелец справочника и событие об изменении.
5. **Идемпотентность.** Терминал может прислать один платёж дважды → `idempotency_key UNIQUE`.
6. **Outbox.** Платёж и событие «платёж получен» пишутся в одной локальной транзакции, отдельный
   процесс доставляет событие в брокер — событие не теряется, даже если брокер был недоступен.
7. **Запросы «через сервисы»** — API Composition (шлюз опрашивает сервисы) или отдельная
   read-модель (CQRS), которая собирается из событий и отстаёт на секунды.

## Сценарий «клиент заплатил в терминале»

```
Терминал ──POST /payments (idempotency_key)──▶ Payment Service
                                              ├─ INSERT payments          ┐ одна локальная
                                              └─ INSERT outbox            ┘ транзакция
Outbox relay ──событие PaymentReceived──▶ Kafka ──▶ Loan Service: UPDATE schedule SET paid = true
                                                 └─▶ Notification Service: SMS клиенту
```

В скрипте этот сценарий выполняется внутри `BEGIN … ROLLBACK`, данные не меняются.
